# ADR-0001 桌面优先与官方服务协同

- **状态**: Proposed
- **日期**: 2026-11-19
- **决策者**: 产品与工程评审
- **关联**: D001、D002、D003

## 背景

Link Studio 需要同时具备桌面创作体验、本地项目/自定义模型、官方 Provider 和可核验积分。若将所有模型调用放在桌面端，官方 Provider 凭证会暴露，且客户端无法作为可信积分核算方；若把所有项目和媒体放到云端，则与默认本地项目及隐私预期冲突。

## 决策

采用本地优先的渐进混合架构：首阶段桌面端掌控创作界面、项目、个人模型调用和任务展示；个人自定义模型由桌面端 Main/Utility Process 使用本地密钥直连。官方模型在后续阶段接入，其请求执行、凭证机制、积分结算和退款语义另行决策。本 ADR 暂为 Proposed。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 所有模型直接由桌面端调用 | 流程统一、服务端实现较少 | 官方密钥难以保护；积分与用量不可信；跨设备任务审计困难 | 不采用 |
| B. 所有模型都由官方服务调用 | 凭证与计费统一 | 用户自定义模型密钥需上传；本地模型/离线能力受限 | 不采用 |
| C. 首阶段交付本地自定义模型，官方模型路径后续评审 | 先跑通桌面创作，避免预设计费协议 | 官方模型后置，后续需要独立设计 | 当前采用的阶段性方案 |

## 后果

- 正面：本地项目无需账号即可使用；官方消费可由服务端权威结算；个人密钥保留在用户设备。
- 负面：桌面端需要维护本地与远端两类任务权威状态及断线恢复逻辑。
- 风险与缓解：官方请求涉及提示词/参考媒体上传 → 任务提交前明确告知并按需上传；重复提交导致重复扣费 → 服务端幂等键和账本唯一约束；自定义 Provider URL 风险 → Main 端验证和受控网络策略。

## 遵守方式

- 官方和自定义模型使用统一的任务视图及不同的 `executionSource`。
- 官方密钥只能由官方服务读取；个人密钥只能由桌面 Main/系统安全存储读取。
- 官方积分和价格以服务端账本及任务记录为准，客户端数值仅为展示。
- 每个任务有幂等 ID、执行来源、Provider/Model ID 和可对账状态。
- 在功能规格中为提交重放、超时未知、退款/释放、凭证泄漏、上传授权和断线恢复补齐 AC 与技术设计。
