## C6：停用后只续查原回执

原版 `channels/index.tsx` 明示「进行中的任务不受影响」，`generation_task_create.go` 说明提交时冻结配置。修复前，桌面用同一启用检查拦截新提交和已提交查询，导致已有回执也进入“结果未知”。现在只有按原任务快照、带回执的查询可以在渠道停用后继续；不改变端点、网络范围、凭证和插件检查，也不授予新提交、排队重试或远端取消的例外。

回环测试：取得视频回执后停用，同渠道另一节点即使用当前修订也无法提交；旧任务在渠道保持停用时自动查询原回执并下载一份产物，无须重开渠道或手动复查，全程一次 POST。另测收到 429 后尚无回执的任务不再提交；原快照不匹配、端点或内网范围变动、必要 Key 已清除时仍拒绝。`pnpm exec vitest run tests/integration/{generation,settings}.test.ts -t 'C6 |撤包恢复数据仅凭原任务|提交退避中迁移并重开|旧任务删除保护'`：9/9。仅改主进程行为，不更新界面截图。

## 旧工程的删除与恢复

原版 `backend/internal/service/ai_plugin_delete.go` 依据服务端引用中的活动任务数阻止整组删除。桌面项目文件保存任务，设置库记录项目已登记的插件和渠道引用。测试在临时目录提交视频，收到回执后停止执行，移除项目中的渠道 ID、设置库中的绑定和引用，再关闭工程、迁移模型并改绑插件，模拟缺字段的历史数据。

| 时点 | 补登记实现前的结果（清单外仍有此限制） |
|---|---|
| 首次重开前 | 旧插件活动任务数为 0，整组删除成功。 |
| 重开后，任务仍在等待查询 | 保留的旧插件按项目中的哈希登记，活动数为 1，整组删除返回 `PLUGIN_JOB_REFERENCED`。缺少渠道 ID 时原渠道仍可删除。 |
| 恢复查询，再手动复查 | 两次均回到“结果未知”，保留复查入口。回环服务只收到初始提交的 1 次 POST，查询 0 次。 |
| 对照用例 | 有快照时迁移并重开，重试继续使用原渠道。已有引用登记时，重开设置库仍能阻止删除。 |

初测使用本机 macOS、Node 22.23.0、SQLite 和 HTTP 回环，4/4 通过。真实旧工程样本与生产回执仍待外验。

### C7 / P6：已知旧工程的删除保护

首次打开设置库时，从最近清单（最多 30 项）取路径与项目 ID，在内置发行清理前只读检查本机 APFS 工程。清单须与快照身份匹配，修订文件名须连续、唯一，当前快照须通过格式及内容哈希检查。只读最新正文，不回放历史正文、不打开项目、不修改 manifest。成功核对的项目记录迁移标记，后续启动不重复导入；失败的不标记。此过程不替代正常打开时的完整恢复检查。

| 临时工程条件 | 启动后的可观察结果 |
|---|---|
| 最近清单有该工程；在途任务有旧插件哈希、无渠道 ID | 重开工程前，插件活动数为 1，单版本和整组删除均拒绝；模型迁移后的目标渠道活动数为 0，不据此阻止原渠道删除。 |
| 同上，任务还保留原渠道 ID | 原渠道活动数为 1，删除返回 `CHANNEL_ACTIVE_JOBS`。两次冷启动计数不叠加，两种情形均未增加调度负载。 |
| 工程正常重开、任务进入结果未知 | 调度器按实际工程状态接管引用；失去在途引用后可删除插件。缺绑定的任务不重提、不向迁移目标发请求。复查入口以 P8 验证为准。 |
| 最近清单无该工程，且此前无登记 | 无从补登记，旧插件仍可被删除。路径改指向、身份不符、manifest 过期或最新快照损坏均不据此生成引用。重复项目 ID 也跳过，不选择其中一份作为权威工程。 |

补登记仅参与删除计数，不补凭证、执行绑定、插件恢复授权或排队名额。已登记的真实引用不因文件不可读而清除；未登记、又无法读取的工程不等于“已确认没有任务”。

定向复现：`pnpm exec vitest run tests/integration/{project-store,generation,settings}.test.ts -t '只读补登记|旧任务删除保护|提交退避中迁移并重开|在途任务保护已解绑'`，6/6。`pnpm exec playwright test tests/e2e/provider-catalog.spec.ts -g '启动清理撤包内置插件'`，1/1，覆盖使用 `recent.json` 的 Electron 冷启动、撤包阻断提示与释放后再启动。主进程类型检查及 Electron 构建通过，无界面改动，不更新截图。

## M6、P8：主进程强制退出后续查

两条路径分别在独立临时目录提交一个异步图片任务。回环服务生成随机回执和游标，在首次收到游标查询时扣住响应；测试对自己启动的 Electron 主进程发送 `SIGKILL` 并确认退出信号，再用同一目录启动新进程。仅在新进程发起续查后才返回 PNG。

| 路径 | 实际请求顺序（每例独立） | 用户可见结果 |
|---|---|---|
| M6 模型试跑 | 提交一次 → 查询原回执 → 查询新游标时强退 → 用原回执和同一游标续查一次 | 重开试跑窗可见 42% 进度，随后显示 `succeeded`，一张图可解码 |
| P8 工程生成 | 同上；重启后从最近项目打开原工程，不点击重新生成 | 画布显示一张可解码图片，任务中心有一条「已完成」 |

复现：构建 Electron 后运行 `pnpm exec playwright test tests/e2e/provider-crash-recovery.spec.ts`。此项只验回执和游标已保存后的主进程中断，不模拟断电，也不证明真实签名过期、供应商计费或像素一致。

## P8：有回执不等于可以复查

**异步 URL 产物的首次转存（原版源码 + 桌面回环）。** 原版 `4277d16f` 的 `worker_poll.go` 在任务成功时标记 `finalizing`，`worker_finalize.go` 的 `finalOutputs` 在没有即时结果时按原任务重新查询，再下载；`worker_submit_test.go` 明确断言了这次额外查询。修复前桌面工程直接下载首次成功查询里的地址。现在先保存「转存中」及供应商状态，再按原回执查询，只下载本次返回的地址。此改动不涉及同步即时结果、纯二进制产物或 M6 试跑。

回环夹具让 `/first` 和 `/fresh` 都能正常下载。完整请求断言为：一次提交 → 原回执查询成功 → 同回执再查 → 仅下载 `/fresh`。另验转存查询挂起时关闭并重开工程、查询暂回运行中，以及新地址返回模拟 403 后再取地址；每种情况均只提交一次、只入库一份。复现：`pnpm exec vitest run tests/integration/generation.test.ts -t '异步视频按原回执取最新 URL'`。

外验分别记录两件事：① 日志中同一任务的提交、成功查询、再次查询和下载顺序；② 如要证明过期恢复，还要有供应商明确的过期原因或可核对的到期时间，以及同一任务刷新后成功下载的证据。单独的 403 不能区分过期与无权限；提前拿到新地址也不证明旧地址下载失败过。归档使用任务别名和相对时间，不保留签名地址或密钥。

原版 `backend/internal/provider/snapshot.go` 冻结提交时的模型、渠道和插件身份。桌面不把“本机无法查询”解释成“供应商已失败”，也不拿迁移后的绑定去查询旧回执。

- **原绑定缺失或不匹配：** 活动任务查询受阻，或重开工程发现旧记录仍标为可复查时，持久化为“结果未知 / 无法查询原任务”。任务中心提示到原供应商核对，不再提供“查询原任务”；主进程拒绝复查。三种清单／渠道记录组合均只收到初始 POST，查询为 0 次。
- **原绑定仍可识别：** 有快照、旧修订仍匹配或插件升级链完整时，不因一次网络断开而关掉复查。已验证查询断连后退出、移除模型、发行撤包、重开工程，仍能按原回执取回视频，全程只提交一次。这项身份判断不是新的端点授权；渠道停用时仅允许上述 C6 原快照回执查询，不替代插件来源和凭证检查。
- **界面行为：** Electron 打开包含两条旧“结果未知”记录的工程。在 1280×800、1024×700 下验证缺绑定的说明可见、按钮不存在，另一条的按钮可用。打开工程请求数为 0；点击可用项，仅发出一次携带原回执的 GET。这是桌面任务中心的可用性验证，不是原版像素对照。

定向复现：`pnpm exec vitest run tests/integration/{generation,settings}.test.ts -t '旧任务删除保护|撤包后重开设置库和工程|停用整组协议拦截新绑定|旧任务有远端回执'`，6/6；`pnpm exec playwright test tests/e2e/generation.spec.ts -g '旧工程结果未知'`，1/1。Electron 构建及 `pnpm typecheck` 通过；未使用生产供应商、未跑全量回放。

## P5：协议升级与手动重新授权

原版 `backend/internal/service/ai_config_upgrade.go` 按插件 key 找旧模型，保留设置，逐个调用 `SaveModel`；失败项保留旧绑定。桌面普通渠道也按模型报告结果；旧共享连接不能只升级组内一部分，目标设置不兼容时整组保持不变。

本轮先复现了一个入口差异：批量升级会拒绝继承旧凭证，但手动保存同一模型可以跳过这一检查。现在对已绑定渠道模型，表单和 JSON 保存均按**实际目标插件**检查鉴权类型、凭证位置和非内置自定义签名代码变更。兼容版本无需额外确认；不兼容版本不能自动升级，操作者可在模型编辑器核对渠道、版本和目标鉴权后单独授权。旧哈希和端点批准都不能代替这次授权。

- 集成测试：`pnpm exec vitest run tests/integration/settings.test.ts -t '手动改绑与批量升级|升级失败说明目标能力|分配版本号并按共享连接|离线渠道模型可保留'`，4/4。
- Electron：`pnpm exec playwright test tests/e2e/model-channels.spec.ts -g '协议鉴权变化|协议升降版保留'`，2/2。1280×800 取消后试跑仍只发旧 Bearer；1024×700 确认后试跑只用新请求头。回环端点使用模拟凭证，弹窗不含明文，取消和确认本身均不发请求。此项验证桌面授权交互，不是原版像素签收。
- Electron 构建与 Web 类型检查通过；Node 类型检查仍有本轮范围外的 `tests/e2e/settings.spec.ts:163` 可空字符串报错。未跑全量回放。

## C1 与 C9：端点授权与平台角色

- **C1 谁确认。** 原版 `channels/channel-dialog.tsx` 允许新建时填写双凭证。桌面也在同一表单填写，但按[冻结决策 D014](../06-决策记录/冻结决策.md#d014-本机-provider-授权与设置助手回执)由本机操作者确认目标端点和本机／内网范围，不能为了外观一致去掉授权步骤。
- **C1 实测。** 修复前，把 `https://fixture.invalid/api` 改写成 `https://FIXTURE.invalid:443/api/` 会提示清除 Key，而主进程认定它们相同。现在保存等价地址不写新修订且保留双凭证；改路径或网络范围仍须确认。只改网络范围时明确提示授权变化，确认后两项旧凭证均已清除。已登记的路径再保存也不逐次丢失末尾斜杠。这里只验行为，不新增像素签收结论。
- **C9 谁管理。** 原版 `web/src/utils/admin/role.ts` 区分模型操作和基础设施写入；`backend/internal/router/router.go` 的 `superOnly` 实际保护渠道写入与插件管理，不只是禁用按钮。桌面受信设置窗口操作本机配置，不获得官方 `super_admin` 身份。[D003](../06-决策记录/冻结决策.md#d003-本阶段不提供工作室自托管和工作室-provider-层) 将官方身份与组织策略留在服务端，[V1 设置助手规格](../03-功能规格/V1/05-内置Agent/08-设置Agent与配置变更单.md)也排除借本机工具取得后台权限。因此本阶段不造模拟角色、不拿桌面按钮充当原版权限证据。若接入官方管理接口，再以两个真实后台角色同时检查服务端拒绝与按钮状态。
- **定向复现。** `pnpm exec vitest run tests/integration/settings.test.ts -t '渠道授权拒绝未确认|方舟备案限官方单渠道|助手渠道概要包含'`，3/3；`pnpm exec playwright test tests/e2e/model-channels.spec.ts -g '等价地址不清除|渠道表单在首次保存后|新增渠道部分凭证'`，3/3。Electron 构建与 `pnpm typecheck` 通过；未跑全量回放或官方账号实测。
