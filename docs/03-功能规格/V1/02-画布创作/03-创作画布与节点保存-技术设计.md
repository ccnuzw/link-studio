# 03 创作画布与节点保存 - 技术设计

来源：[需求](03-创作画布与节点保存.md#需求说明) · [接口](03-创作画布与节点保存.md#接口契约) · [数据](03-创作画布与节点保存.md#数据与事务) · [验收](03-创作画布与节点保存.md#验收标准)

## 风险与对策

| 风险 | 严重程度 | 对策 | 关联决策 |
| --- | --- | --- | --- |
| 自动保存丢失并发更改 | 高 | revision 乐观锁、保留 dirty buffer | D001 |
| 上游 schema 迁移丢字段 | 高 | 原始未知字段保留、迁移 fixture | D001 |
| 大节点 payload 卡 UI | 中 | Blob 外置、IPC payload 上限和批量操作 | D001 |

## 单元契约

| 函数 | 前置条件 | 返回 / 后置条件 | 副作用 | 幂等 |
| --- | --- | --- | --- | --- |
| `applyCanvasOperations({ projectHandle, expectedCanvasRevision, operationId, operations })` | 受信窗口持有项目会话，操作通过 schema | 画布与项目的新修订 | 写本地项目 | 同 ID 同指纹返回首次修订 |

## 伪代码

```text
FUNCTION applyCanvasOperations(expectedCanvasRevision, operationId, operations):
  verify owner and reject invalid operation payload            // B03-01
  recover pending commit and check operation receipt
  IF current canvas revision differs: RETURN CANVAS_REVISION_CONFLICT // B03-03
  resolve referenced assets, reject missing or wrong media type // B03-02
  apply operations to draft and validate final graph            // B03-04
  persist graph, both revisions and receipt atomically           // B03-05
  return project revision and canvas revision
```

## 并发控制

项目协调器与 `ProjectStore` 写队列串行提交。画布 CAS 只检查 `expectedCanvasRevision`，重命名和素材导入只推进项目修订。Renderer 合并修订时取较新项目修订。编辑停止约 450 ms 后提交，拖动过程暂缓。自动保存失败暂停定时提交并显示恢复操作。

## 事务边界

操作校验、draft 应用、快照原子写和 revision 更新构成一次本地提交；写入失败保留前一快照和 Renderer dirty buffer。

## 幂等与重试

`operationId` 与规范化请求指纹写入同一个快照。结果不确定时先核对可恢复快照链及同一批回执，再尝试提交后续草稿。冲突时按节点 ID、边 ID、视口检测重叠，明确合并非重叠改动后仍经 Main 做图校验与 CAS。

## 外部调用与补偿

不适用：画布服务不直接调用网络 Provider。

## 安全与日志

IPC 只接收白名单结构化操作；节点数据大小、字符串长度和数组深度设置限制。日志不落画布正文。

常规画布最多 1,000 节点与 4,000 连线。组成员采用相对坐标，分组结构为单层。S2 每个创作节点有一个入端与出端，拒绝自连、重复有向连线及非创作端点。节点编辑不修改任务、分镜或素材记录。

## 发布与回滚

继续使用 `ProjectState` 和画布 schema v1。历史快照不可变。可识别的 S1 `creative` 节点直接读取。既有未知节点及边保存在原始记录中，投影只提供位置、标题与可解析连线供只读显示。
